# SpaceX 第1段ロケットの着陸成否予測

打ち上げの条件から、ロケットの1段目を回収できるかどうかを予測する。
IBM Data Science Professional Certificate の最終課題（2023年8月）を出発点に、
分析ロジックを再利用できる形へ整理し直したもの。

---

## Why — 何を解く分析か

ロケットの打ち上げ費用の大部分は機体そのものの製造費で、1段目はその中でも
最も高価な部分にあたる。1段目を着陸させて回収できれば次の打ち上げに使い回せるため、
**回収できるかどうかは、そのまま1回の打ち上げの原価を左右する**。

したがって「この条件の打ち上げなら回収できる見込みがあるか」を事前に見積もれると、
費用の見積もりが立つ。それがこの分析の目的である。

予測に使うのは、打ち上げ前に分かっている条件だけ。

- 積荷の重量と投入先の軌道
- 発射場
- 使う機体の世代・これまでの飛行回数・再使用回数
- 着陸脚や姿勢制御翼を備えているか

## Design Choice — 構成と、その理由

### 1. 「考えた記録」と「再利用する部品」を分ける

```text
notebooks/   分析を進めたときの記録。当時のまま残す
src/         そこから切り出した、何度でも同じ結果を出せる部品
tests/       部品の振る舞いを固定する検査
data/        入力と中間生成物
reports/     発表資料
```

ノートブックは上から順に読むと分析の流れが追える形になっており、
**試行錯誤の過程そのものに価値がある**ため、書き換えずに残している。
一方、そこに書かれた処理をもう一度使いたいときは、セルをコピーするのではなく
`src/` の関数を呼ぶ。同じ処理が2か所にあると、片方だけ直したときに
結果が食い違う。

### 2. 外部サービスへの依存を、境界の1か所に閉じ込める

データの取得元は SpaceX の Web API と Wikipedia の2つで、どちらも
こちらの都合とは無関係に変わる。そこで「URL を渡すと結果が返るもの」という
約束だけを決めておき、実際の通信手段は外から渡す形にした。

```python
collector = SpaceXLaunchCollector(fetch=HttpJsonFetcher())  # 本番
collector = SpaceXLaunchCollector(fetch=用意した応答を返すもの)  # 検査
```

この形にしたことで、**検査は一度もネットワークに接続しない**。
接続してしまうと、検査が落ちたときに原因が「自分のコードの誤り」
「相手の障害」「相手のデータの変更」の3つに増えて切り分けられなくなる。

副産物として、同じ ID を二度引かない仕組みを入れられた。
データ収集にかかる通信は 360 回から 十数回に減っている。

### 3. 標準化を学習の流れの内側に入れる（元の手順からの変更点）

説明変数は単位がばらばら（重量は数千、飛行回数は1桁）なので、
各列を平均 0・ばらつき 1 に揃える処理（標準化）を挟む。

このとき **標準化の基準値をどのデータから計算するか** が問題になる。

```text
元の手順:  全データで基準値を計算 → 訓練用と検証用に分割 → 学習
この版  :  訓練用と検証用に分割 → 訓練用だけで基準値を計算 → 学習
```

元の手順では、検証用データの情報（平均とばらつき）が学習側に混ざる。
本番では未知のデータを予測するのに、検証のときだけ答えの一部を先に見ている
ことになり、**成績が実力より良く出る**。

この版では標準化とモデルを1つの流れにまとめ、その流れごと分割・学習させている。
そのため後述の数値は、元のノートブックの数値と一致しない。

### 4. 探索する範囲の定義と、学習の実行を分ける

「どの設定値を試すか」は機械学習ライブラリを使わずに書ける。分けておくと、
探索の規模（この分析では 831 通り・学習 8,310 回）を **1件も学習させる前に**
確認できる。範囲を広げるときに、うっかり実行時間を100倍にすることがない。

### 5. 乱数の種を固定する

決定木は、分割に使う特徴量を無作為に選ぶ設定（`max_features='sqrt'`、
`splitter='random'`）を探索範囲に含む。種を固定しないと、**同じデータ・同じコードで
実行するたびに結果が変わる**。

整理の途中で実際に起きたことを記録しておく。種を固定する前、
同じスクリプトを2回走らせた結果は次のように振れた。

| 実行 | 交差検証 | 検証データの正解率 |
|---|---|---|
| 1回目 | 0.905 | 0.722 |
| 2回目 | 0.916 | 0.667 |

正解率で 5.5 ポイントの差がある。この状態でモデルを改良しても、
**良くなったのか偶然良く出たのかを区別できない**。

現在は種を固定してあり、2回実行して出力が1バイトも変わらないことを確認している。
種を固定し忘れたときに気づけるよう、テストにも入れてある
（`tests/test_modeling.py` の「同じ設定で二度学習しても同じ結果になる」）。

## 結果

分析対象は 90 件（訓練 72 件 / 検証 18 件）。説明変数は 80 列。

**比較の基準**：着陸に成功した打ち上げは全体の 66.7% である。つまり
「常に成功と答える」だけで正解率 66.7% になる。この値を超えて初めて、
モデルが何かを学んだと言える。

以下の数値は次のコマンドで再現できる（所要数分）。

```sh
uv run python ibm-capstone-spacex/scripts/run_pipeline.py
```

### 交差検証（訓練データを10分割して測った平均正解率）

| モデル | 平均正解率 | 選ばれた設定 |
|---|---|---|
| 決定木 | 0.891 | 深さ2・無作為分割 |
| k近傍法 | 0.868 | 近傍8件・マンハッタン距離 |
| サポートベクターマシン | 0.850 | 線形カーネル |
| ロジスティック回帰 | 0.836 | C=0.1 |

### 検証データ（18件）での成績

| モデル | 正解率 | 適合率 | 再現率 | F1 | 見逃し | 誤検知 |
|---|---|---|---|---|---|---|
| 決定木 | 0.833 | 0.800 | 1.000 | 0.889 | 0 | 3 |
| k近傍法 | 0.833 | 0.800 | 1.000 | 0.889 | 0 | 3 |
| ロジスティック回帰 | 0.778 | 0.786 | 0.917 | 0.846 | 1 | 3 |
| サポートベクターマシン | 0.778 | 0.786 | 0.917 | 0.846 | 1 | 3 |

### この結果の読み方

**4つのモデルの優劣は、この結果からは決められない。**

検証データが 18 件しかないため、1件当たり外れが変わるだけで正解率は 5.6 ポイント動く。
上位と下位の差（0.833 と 0.778）は、ちょうど1件分でしかない。

これは推測ではない。上の「乱数の種を固定する」で書いたとおり、
**種を変えただけで決定木の正解率は 0.667・0.722・0.833 と振れた**。
モデルの違いではなく、たまたまの分かれ方でこれだけ動く規模のデータだということ。

より確かなことが2つ言える。

1. **どのモデルも、比較の基準（0.667）は上回っている。**
   打ち上げの条件から回収可否をある程度は見積もれる、とは言える。
2. **誤検知（回収できると予測して外した）が全モデルで3件ある。**
   18 件中3件、つまり6件に1件の割合。費用の見積もりに使うなら、
   この誤りは「回収前提で組んだ予算が崩れる」ことを意味する。
   正解率よりこちらのほうが実害に直結する。

## 既知の限界

- **説明変数が訓練データより多い（80 列 対 72 件）。**
  主因は機体の個体番号（`Serial`）をダミー変数化して 60 列以上に開いていること。
  元の分析の手順に合わせて残しているが、実務に載せるなら落とすか、
  機体の世代（`Block`）に集約するのが妥当である。
- **対象期間が 2020年11月13日まで。** 2つのデータ源で期間を揃えるための制約であり、
  それ以降の運用の変化は反映されていない。
- **検証データが 18 件。** モデルの優劣を断定できる規模ではない。
  結論を強くしたければ、分割を変えて繰り返す方法（交差検証の入れ子）が要る。
- **`reports/` の発表資料は 2023 年 8 月時点のもの。**
  上記の数値は今回の整理で測り直したものなので、資料の記載とは一致しない。

## How-to — 動かし方

このプロジェクトは、リポジトリ全体で1つの環境を共有している。
以下はリポジトリの最上位で実行する。

```sh
uv sync                      # 環境を作る（初回のみ）
uv run pytest                # 検査を走らせる（104 件）
uv run ruff check .          # 書き方の検査
```

ノートブックを開いて実行する場合は、追加のライブラリが要る。

```sh
uv sync --extra notebooks
uv run jupyter lab
```

`src/` の部品を対話的に使う例：

```python
import pandas as pd
from spacex_capstone.preprocessing.features import build_feature_matrix
from spacex_capstone.modeling.training import (
    default_model_specs,
    split_train_test,
    train_all,
)

frame = pd.read_csv("data/processed/dataset_part_2.csv")
features = build_feature_matrix(frame)
x_train, x_test, y_train, y_test = split_train_test(features, frame["Class"])
results = train_all(default_model_specs(), x_train, y_train)
```

### 保存時に変更した点

元は IBM が提供するブラウザ内の実行環境（JupyterLite）で書かれており、
そのままでは手元で開いても動かない。分析の内容は変えず、次の2点だけを差し替えた。

1. `import piplite` / `await piplite.install(...)` … ブラウザ内 Python への
   パッケージ導入命令。手元では不要なため削除した
2. `from js import fetch` … ブラウザの通信機能を呼ぶ命令。
   リポジトリ内の CSV を読む形に差し替えた
   （`06` が使うデータだけはリポジトリに含まれないため、URL からの読み込みに変更）

あわせて、保存先・読み込み先のパスを `data/` 以下の構成に合わせた。
